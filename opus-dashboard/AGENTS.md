## Database Rules — Convex (`convex/schema.ts`)

These rules are non-negotiable. Every violation creates a multi-tenancy security bug or data integrity issue.

### 1. `orgId` on everything

Every table has an `orgId` field. Every query and mutation **must** filter by `orgId`. Never fetch documents without scoping to the current org. This is enforced at the query level — never rely on UI or middleware alone.

```typescript
// ✅ Correct
const bookings = await ctx.db
  .query("bookings")
  .withIndex("by_org", (q) => q.eq("orgId", orgId))
  .collect();

// ❌ Wrong — never query without orgId
const bookings = await ctx.db.query("bookings").collect();
```

### 2. Soft deletes only

Never hard-delete documents. Set `isDeleted: true` and `deletedAt: Date.now()`. Always filter out soft-deleted records in queries unless explicitly building an admin/audit view.

```typescript
// ✅ Correct
.filter((q) => q.eq(q.field("isDeleted"), false))

// ❌ Wrong
await ctx.db.delete(bookingId);
```

### 3. Money is always minor units (integers)

All monetary values are stored as integers in minor units (pence, cents). `2500` = £25.00. Never use floats for money. Never store formatted strings like `"£25.00"` in the database.

```typescript
// ✅ Correct
priceMinorUnits: 2500; // £25.00

// ❌ Wrong
price: 25.0;
price: "£25.00";
```

### 4. Timestamps are Unix milliseconds

Use `Date.now()` everywhere. Never store ISO strings or Date objects in Convex.

```typescript
// ✅ Correct
createdAt: Date.now();

// ❌ Wrong
createdAt: new Date().toISOString();
```

### 5. Booking writes must use transactions

When creating a booking, you **must** check for slot conflicts inside the same Convex mutation using the `by_staff_start` index. Two concurrent requests for the same slot must resolve to exactly one booking. Convex mutations are serialised — use this guarantee.

```typescript
// Inside a mutation — check before writing
const conflict = await ctx.db
  .query("bookings")
  .withIndex("by_staff_start", (q) =>
    q.eq("staffId", staffId).eq("startAt", startAt),
  )
  .filter((q) => q.neq(q.field("status"), "cancelled"))
  .first();

if (conflict) throw new ConvexError("Slot already booked");
```

### 6. Write to `audit_log` on every significant mutation

Bookings, cancellations, and AI-triggered actions must write an `audit_log` entry. The log is append-only: never update or delete audit rows. Always include `before` and `after` snapshots where applicable.

```typescript
await ctx.db.insert("audit_log", {
  orgId,
  actorType: "ai",
  actorId: "claude",
  action: "booking.created",
  resourceType: "bookings",
  resourceId: bookingId,
  before: null,
  after: newBooking,
  createdAt: Date.now(),
});
```

## Authentication & Authorisation

- Auth is handled by **Better Auth** with passwordless email OTP. The Convex `ctx.auth` object carries the authenticated user identity.
- Always resolve `orgId` from the authenticated session — never accept it as a raw user-supplied argument to mutations.
- The `staff_members` table is the permission boundary. A user's role (`owner`, `manager`, `staff`) is org-scoped and must be checked before any sensitive mutation.
- Customers are **not** platform users. They do not have authenticated accounts. Never mix up the `users`, `staff_members`, and `customers` tables.

```typescript
// Resolve orgId safely — never trust client-supplied orgId
const identity = await ctx.auth.getUserIdentity();
if (!identity) throw new ConvexError("Unauthenticated");

const staffMember = await ctx.db
  .query("staff_members")
  .withIndex("by_org_user", (q) => q.eq("orgId", orgId).eq("userId", userId))
  .first();

if (!staffMember || staffMember.isDeleted)
  throw new ConvexError("Unauthorised");
```

## Tenant Website Routing

The authenticated dashboard lives at `studio.opus.mk`. Each published business gets one automatic website such as `studio-luna.opus.mk`; custom domains are not an active feature.

Root `proxy.ts` parses the single tenant label and rewrites it to `/sites/{slug}` without querying Convex. The public page resolves the slug through the `by_slug` index and returns data only for an active, beauty-only, website-published organization. Reserve platform labels such as `studio`, `www`, `api`, `app`, and `admin`. A slug is frozen after the website is first published.

Website publication uses `websiteStatus` and is independent from dormant marketplace `listingStatus`. Never couple the two states. The legacy `customDomain` field may remain temporarily for stored-document compatibility, but it must not have active UI, mutation, query, or routing behavior.

**Never hardcode org-specific values anywhere in shared components.** All branding (colors, logo, name) must be read from the resolved org context.

## Dormant AI Agent Foundations

AI front-desk work is P2 and not part of the active product promise. Preserve the existing safety rules, but do not expand or market this foundation without explicit authorization and verified provider configuration.

### Confidence threshold

Every AI response must include a `confidenceScore` (0–1). If the score is below `org_settings.aiConfidenceThreshold` (default `0.7`), the conversation must be flagged as `handed_off` and a human notified. Never let a low-confidence AI response go out unreviewed.

### AI must never directly mutate bookings

AI actions call Convex **Actions** (not mutations directly). The action validates the intent, checks availability, and calls the appropriate mutation. This keeps the audit trail clean and ensures all booking rules, including conflict checks, are enforced uniformly regardless of source.

### Log every AI action

Every message the AI sends and every action it triggers (booking created, rescheduled, or cancelled) must be written to both `ai_messages` and `audit_log`. This is mandatory — not optional.

### System prompt context

When calling Claude, always inject:

- Current shop schedule and available slots
- Customer history (visits, no-show score, preferred staff)
- Business tone guidelines from `org_settings.aiPersonaName`
- Cancellation policy
- Never inject raw database IDs into the prompt — resolve them to human-readable labels first.

## Notifications

Outbound notifications (SMS, email, WhatsApp) use the `notifications` queue when the corresponding provider is configured. Do not call Twilio, Resend, or Sender directly from mutations — always write to the queue and let the scheduler handle delivery. Never claim delivery without configured providers and verified results.

## Coding Conventions

- **TypeScript everywhere** — no `any` except in `audit_log.before/after` snapshots and `notifications.templateData`, which are intentionally open.
- **Convex validators** — all mutation arguments must use `v.*` validators. Never accept raw unvalidated input.
- **No business logic in components** — React components call Convex queries/mutations. Logic lives in Convex functions.
- **Error handling** — use `ConvexError` for user-facing errors (they are returned to the client). Use `throw new Error` for internal unexpected failures (they are logged server-side).
- **Named indexes** — always query via a named index (`.withIndex(...)`). Never use `.filter()` as the primary data access path — it is a full table scan.
- **Formatting** — Prettier with default config. Run before committing.

## What NOT to Do

- **Do not** query any table without an `orgId` filter.
- **Do not** hard-delete any document — soft deletes only.
- **Do not** store floats for money.
- **Do not** call Twilio, Resend, or Sender from inside a Convex mutation — use Actions for all external API calls.
- **Do not** trust client-supplied `orgId` values — always derive from the authenticated session.
- **Do not** let the AI send a response without logging it to `ai_messages`.
- **Do not** edit anything in `convex/_generated/` — it is auto-generated by the Convex CLI.
- **Do not** add new tables to `schema.ts` without a corresponding index on `orgId`.

## Key Domain Concepts Glossary

| Term                    | Meaning                                                                         |
| ----------------------- | ------------------------------------------------------------------------------- |
| `org`                   | A business on the platform (e.g. "King Cuts Barbershop")                        |
| `staff_member`          | A user scoped to an org with a role (owner / manager / staff)                   |
| `customer`              | An end-client of the business — not a platform user                             |
| `service`               | A bookable item with a price and duration (e.g. "Men's Haircut — 30 min — £25") |
| `availability_rule`     | Recurring weekly hours for a staff member                                       |
| `availability_override` | A one-off date-specific exception (day off, different hours)                    |
| `booking`               | A confirmed (or pending) appointment tying customer + staff + service + slot    |
| `ai_conversation`       | A thread of AI ↔ customer messages on a given channel                           |
| `surge pricing`         | Automatic price increase during configured high-demand windows                  |
| `handoff`               | When AI confidence drops below threshold and a human takes over                 |
